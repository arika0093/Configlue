---
title: State instances, profiles, and subjects
description: Choose between the default state, named states, persisted profiles, and subject scoping, and combine them correctly.
---

Configlue has one state model with three orthogonal concepts. Each has exactly one purpose:

- **State instance** (`TModel` + optional `StateName`): independently addressed runtime state for one model.
- **Profile** (`IConfiglueProfiledState<T>` + `ConfiglueProfileCatalog`): persistence and active-selection management *over* named state instances.
- **Subject** (`ISubjectState<T>.ForSubject(...)`): per-operation scope *inside* one state instance (who or what the operation is for).

## Identity and scope

```text
Configlue model -> StateName (instance) -> Subject (scope)
    -> source-specific ResourceKey / Route -> physical ResourceId
```

- `StateName` selects the **instance**. The default (unnamed) instance uses `stateName: null`.
  `ConfiglueContext.GetState<T>(stateName)` and `ConfiglueApp.GetState<T>(stateName)` address it.
- `Subject` scopes an **operation** inside that instance. It never selects another instance.
  The same state definition serves every subject, while each subject can resolve different
  provider keys, routes, and physical resources.
- A **profile** is catalog-managed membership plus an active selection over `StateName` identities.
  The catalog (`ConfiglueProfileCatalog`) is the source of truth; the dynamic-state registry
  (`IConfiglueStateRegistry<T>`) is only a materialization cache. Unloading a runtime from the
  registry does not delete the profile, and reading a profile re-materializes its runtime.

Diagnostics keep these dimensions separate: events, details resolutions, and write receipts report
the state name and the subject key independently of source identity (`SourceId`) and physical
resource identity (`ResourceId`).

## Usage guidance

Use the **default state** when the application has one settings instance:

```csharp
var settings = ConfiglueApp.GetState<AppSettings>();
var current = await settings.GetValueAsync();
```

Use a **named state** when the application has multiple independently addressed instances of the
same model:

```csharp
await using var context = ConfiglueApp.CreateContext(builder =>
{
    builder.Add<AppSettings>(model =>
    {
        model.StateName = "game";
        model.Sources(sources => { /* ... */ });
    });
});

var game = context.GetState<AppSettings>("game");
```

Use **dynamic named states** (`IConfiglueStateRegistry<T>`) when instance names are only known
at runtime. Use **profiles** (`IConfiglueProfiledState<T>`) when those named instances are
persisted and user-managed, and one of them can be active:

```csharp
var profiles = context.GetProfiledState<AppSettings>();
await profiles.CreateProfileAsync("Work", copyFrom: "default");
await profiles.SetActiveProfileAsync("Work");
var active = await profiles.GetActiveProfileAsync();
```

Use **subjects** when the same logical state definition varies by tenant, user, request, device,
or similar, and provider addressing depends on that scope:

```csharp
var scoped = context.GetSubjectState<AppSettings>().ForSubject(currentUser);
var value = await scoped.GetValueAsync();
```

Single-settings usage exposes none of this vocabulary: `GetState<T>()` with no name, no registry,
no catalog, and no subject is the whole API until you opt into one of the dimensions above.

## Composition

Profiles and subjects compose deterministically: first address the state instance (directly or
through the active profile), then scope the operation to a subject.

```csharp
var profiles = context.GetProfiledState<AppSettings>();
var activeInstance = await profiles.GetActiveProfileAsync();

var scoped = ((ISubjectState<AppSettings>)activeInstance).ForSubject(currentUser);
var value = await scoped.GetValueAsync();
var receipt = await scoped.SaveAsync(patch => { patch.Theme = "Dark"; });

// The receipt reports state-name identity and subject scope separately
// from source and physical resource identity.
Console.WriteLine($"{receipt.StateName} {receipt.SubjectKey}");
```

Two named states for the same subject stay independent. Two subjects of the same named state
share one state definition but can resolve different provider keys and routes. Because profiles
*are* named-state identities, a profile survives registry unload and re-materializes on demand,
and combining a profile with a subject always resolves the same instance scoped to the same
subject key.

## API map

| Need | API |
| ---- | --- |
| Default instance | `GetState<T>()` |
| Named instance | `GetState<T>(stateName)`, keyed DI under the state name |
| Dynamic named instances | `IConfiglueStateRegistry<T>` |
| Persisted named instances + active selection | `IConfiglueProfiledState<T>`, `ConfiglueProfileCatalog` |
| Scope operations to tenant/user/request/device | `ISubjectState<T>.ForSubject(subject)`, current-subject accessors |
| Registration topology | `ConfiglueStateDiagnostics.StateName` (subject-independent) |
| Per-operation identity | `ConfiglueDiagnosticEvent.StateName` + `SubjectKey`, details `Resolution`, `StateWriteReceipt.StateName` + `SubjectKey` |
