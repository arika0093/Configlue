---
title: Vault KV secrets
description: Use a HashiCorp Vault KV secret as a normal Configlue source with version-aware reads and check-and-set writes.
---

One Vault KV secret backs one serialized Configlue payload. The normal codec pipeline
(JSON, MessagePack, XML, YAML) converts between the secret bytes and typed state, so
nested members, sparse/missing/null semantics, and layering work exactly as they do for
file or S3 sources.

```csharp
sources.FromVaultKv(new VaultKvSourceOptions
{
    Mount = "secret",
    Path = "config/app",
    Client = vaultKvClient, // externally owned; carries its own auth
    Codec = StateCodecBinding.Typed(new JsonStateCodec<AppSettings.Fragment>()),
});
```

## KV v1 and v2

- **KV v2** (the default) exposes the secret version as the Configlue revision. Writes
  accept a baseline version and use check-and-set; a stale version becomes a normal
  `StateConflictException` instead of overwriting a newer secret.
- **KV v1** has no versions. Reads report a content-hash revision, and conditional
  writes are verified against a fresh read, which is documented as non-atomic.
  Select it with `ResourceOptions = new VaultKvResourceOptions { KvVersion = VaultKvEngine.V1 }`.

Missing, deleted, and destroyed secrets all read as "not found", so lower-priority
sources are tried under the default fallback condition. Vault performs no multi-path
transactions, so commits spanning several Vault paths keep the normal partial-write
semantics used elsewhere in Configlue.

## Change observation

Vault KV has no streaming watch. The source polls secret metadata (v2) or content (v1)
without re-downloading payloads when metadata is sufficient. Tune the interval with
`PollingInterval` (minimum one second, default five seconds) or disable watching with
`EnableWatch = false`.

## Authentication

The provider performs no login. Inject a preconfigured `IVaultKvClient` (or a
`ClientFactory` that resolves one) whose transport already carries its credential, for
example an `HttpClient` wrapper that injects an `X-Vault-Token` header. Token,
AppRole, Kubernetes, cloud, and custom renewal flows all live outside the provider.

Secret values and tokens never appear in exceptions, diagnostics, provenance
(`vault:{mount}/{path}` plus version), or `ToString()`.

## Least-privilege policies

Read-only usage needs metadata plus read on the exact path:

```hcl
path "secret/metadata/config/app" {
  capabilities = ["read"]
}
path "secret/data/config/app" {
  capabilities = ["read"]
}
```

Writable usage additionally needs update on the data path (check-and-set is enforced
by the provider passing the expected version; no extra Vault capability exists for it):

```hcl
path "secret/metadata/config/app" {
  capabilities = ["read"]
}
path "secret/data/config/app" {
  capabilities = ["read", "update"]
}
```

Scope each policy to the exact mount and path the source addresses, and prefer
short-lived credentials with an explicit `max_ttl`.
