## What is Configlue

The name is **Config + glue**: a library that sticks settings together like glue.

Application settings never live in one file for long. Shipped defaults, per-user files, company-wide policy, container environment variables, command-line overrides for debugging — each has a different location, owner, and lifetime. Configlue plays the glue role: every source contributes only the fields it knows, and they are assembled at runtime into one typed model. From application code, everything still looks like an ordinary C# class.

## Settings are hard

The pain of settings is rarely the amount of read/write code. Over time, it is usually one of these:

- What started as a single JSON grows per-user, per-environment, and policy layers, until nobody knows where a value came from.
- Because the code replaces the whole file, saving one field breaks another. Comments and formatting disappear too.
- Every environment-variable or command-line override scatters another priority rule through the code.
- As soon as a field is added or renamed, old files have no clear handling, and migration becomes "someday" work.

Configlue assumes settings *will* grow. Keep one source per origin, layer only the fields that exist, and write back to a chosen source. Then new sources can be added later without throwing old files away.

## Features

<CardGrid stagger>
  <Card title="Never loads everything at once" icon="layers">
    Instead of reading the whole configuration in one go, each source offers only the fields it owns. A missing field stays missing, so "unset" is never confused with "set to default".
  </Card>
  <Card title="Keeps every value traceable" icon="magnifier">
    Values travel with their origin. You can trace which source provided `Database.Host`, and pick the destination when saving. Sources you did not touch stay untouched.
  </Card>
  <Card title="Built for integration and migration" icon="arrow-right">
    File splitting, shared sections, remote references, versioned schemas, and storage moves all follow the same idea. Locations and shapes can change without rewriting how the app reads and writes.
  </Card>
  <Card title="Works with or without DI" icon="puzzle">
    The same model and source definitions run in plain console or desktop apps and in DI-based ASP.NET Core or Worker Services. Values can also be consumed as `IOptions<T>`.
  </Card>
  <Card title="Feels like plain C#" icon="pencil">
    You read an ordinary class instance and write a generated Patch with `SaveAsync(patch => patch.Name = "Ada")`. The patch names the sparse members to set or unset.
  </Card>
  <Card title="Ready for production" icon="approve-check">
    Change notifications, validation, safe saving with backups, JSON Schema export, and NativeAOT support are included. Start small and carry the same setup into production.
  </Card>
</CardGrid>
