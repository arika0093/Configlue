## Configuration starts simple

One JSON file does not need a configuration framework. Read it, deserialize it, change it, and write it back.

The difficulty appears when the application grows and configuration becomes infrastructure.

<CardGrid stagger>
  <Card title="Git" icon="layers">
    Even a CLI needs system, global, local, worktree, and command scopes. Reading follows precedence rules; writing needs a target scope.
  </Card>
  <Card title="Visual Studio Code" icon="puzzle">
    User, remote, workspace, folder, language, profile, policy, and synchronized settings all coexist, while humans still edit JSON directly.
  </Card>
  <Card title="Chrome" icon="magnifier">
    User preferences can coexist with centrally managed policy, different ownership levels, precedence, and values the user may not be allowed to change.
  </Card>
</CardGrid>

Your application may never become Git, VS Code, or Chrome. But configuration systems grow in the same directions: more scopes, more owners, more persistence rules, more schema changes, and more edge cases around writes.

Eventually you need to answer questions such as which source wins, where an update should be written, whether a value is missing or explicitly `null`, how old schemas migrate, how comments survive a save, and what happens when another process changes the same state.

Configlue handles that configuration plumbing.

## Reading is solved. Writing is the missing half.

.NET already has strong read-side abstractions. `IConfiguration` composes providers, and `IOptions<T>` gives application code typed values.

Applications that *edit* configuration need another boundary.

A settings screen should not need to know whether `Theme = "Dark"` belongs in a JSON file, browser storage, PostgreSQL, a user-scoped file, or another writable source.

Configlue exposes that boundary as typed state:

```csharp
IReadOnlyState<AppSettings>
IWritableState<AppSettings>
```

Your application says what to read or write. Infrastructure decides how.

## The API your application sees

Most application code can stay this small:

```csharp
var settings = ConfiglueApp.GetState<AppSettings>();

var current = await settings.GetValueAsync();

await settings.SaveAsync(patch =>
{
    patch.Theme = "Dark";
});
```

Source layout, serialization, write routing, migration, validation, encryption, and hosting integration remain outside application logic.

## What Configlue handles

<CardGrid stagger>
  <Card title="Typed read/write state" icon="pencil">
    Depend on `IReadOnlyState<T>` or `IWritableState<T>` instead of storage and serialization details.
  </Card>
  <Card title="Layered configuration" icon="layers">
    Combine user, local, environment, command-line, remote, database, and custom sources while retaining provenance and editability.
  </Card>
  <Card title="Sparse writes" icon="pencil">
    Generated patches preserve missing, default, `null`, set, and unset semantics instead of blindly rewriting the whole model.
  </Card>
  <Card title="Schema evolution" icon="arrow-right">
    Version models, migrate old schemas, reshape stored data, validate values, and export JSON Schema.
  </Card>
  <Card title="Production persistence" icon="approve-check">
    Change notifications, safe saves, backups, conflict handling, comments where supported, encryption, and compression are available when needed.
  </Card>
  <Card title="Broad .NET integration" icon="puzzle">
    Use the same state model across plain .NET, DI, Microsoft Options, ASP.NET Core, Blazor, desktop UI, MAUI, Unity, Godot, R3, and NativeAOT scenarios.
  </Card>
</CardGrid>

## One state model, every kind of .NET app

<CardGrid>
  <Card title="Plain .NET" icon="layers">
    Initialize once with `ConfiglueApp.Initialize(...)`, then access process-wide typed state through `ConfiglueApp.GetState<T>()`.
  </Card>
  <Card title="Generic Host & ASP.NET Core" icon="puzzle">
    Register Configlue through DI and inject only `IReadOnlyState<T>` or `IWritableState<T>`. Host integration can add subject-aware state for users or tenants.
  </Card>
  <Card title="Blazor & desktop UI" icon="pencil">
    Use Blazor `StateReader<T>` / `StateEditor<T>` or the shared ComponentModel adapters, with host-native dispatcher integration.
  </Card>
  <Card title="MAUI, Unity & Godot" icon="arrow-right">
    Keep the same state abstraction while each host supplies the correct application paths, lifecycle, storage, threading, and runtime semantics.
  </Card>
</CardGrid>

## Start here

The [README quick start](https://github.com/arika0093/Configlue#quick-start) contains the smallest runnable example and installation instructions.

Start with the high-level state API. Add providers, resources, transformers, hosting packages, or lower-level configuration only when your application actually needs them.
