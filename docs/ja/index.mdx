## 設定は簡単なところから始まる

JSON ファイルがひとつだけなら、設定管理ライブラリは必要ありません。読み込み、デシリアライズし、値を変えて、書き戻せば十分です。

難しくなるのは、アプリケーションが成長して設定管理そのものが infrastructure になったときです。

<CardGrid stagger>
  <Card title="Git" icon="layers">
    CLI であっても system、global、local、worktree、command と複数の scope を持ちます。読み取りには優先順位があり、書き込みでは対象 scope を決める必要があります。
  </Card>
  <Card title="Visual Studio Code" icon="puzzle">
    User、Remote、Workspace、Folder、language、profile、policy、同期設定が共存し、その一方で人間が JSON を直接編集する使い方も残っています。
  </Card>
  <Card title="Chrome" icon="magnifier">
    ユーザー設定と中央管理された policy が共存し、所有者や優先順位が異なり、ユーザー自身には変更できない値もあります。
  </Card>
</CardGrid>

あなたのアプリが Git、VS Code、Chrome ほど大きくならなくても、設定は同じ方向に成長します。scope が増え、設定の所有者が増え、永続化ルールが増え、schema が変わり、書き込み時の edge case が増えていきます。

どの source を優先するのか。変更をどこへ書くのか。値が存在しないことと明示的な `null` をどう区別するのか。古い schema をどう移行するのか。保存時にコメントをどう維持するのか。同じ状態を別プロセスが変更したらどうするのか。

Configlue は、こうした configuration plumbing をアプリケーションから引き受けます。

## 読み取りには抽象化がある。書き込みにも必要になる

.NET には優れた read-side abstraction があります。`IConfiguration` で複数 provider を統合でき、`IOptions<T>` ならアプリケーションから型付きの値として利用できます。

一方、設定を *変更する* アプリケーションには、もうひとつ境界が必要です。

設定画面で `Theme = "Dark"` に変更するとき、その値を JSON、browser storage、PostgreSQL、ユーザー単位のファイル、あるいは別の writable source のどこへ保存するかまでアプリケーション層が知る必要はありません。

Configlue は、その境界を型付き state として提供します。

```csharp
IReadOnlyState<AppSettings>
IWritableState<AppSettings>
```

アプリケーションは「何を読むか・何を書くか」だけを指定し、「どう実現するか」は infrastructure 側で構成します。

## アプリケーションから見える API

普段のアプリケーションコードは、この程度に保てます。

```csharp
var settings = ConfiglueApp.GetState<AppSettings>();

var current = await settings.GetValueAsync();

await settings.SaveAsync(patch =>
{
    patch.Theme = "Dark";
});
```

source の構成、serialization、write routing、migration、validation、encryption、hosting integration はアプリケーションロジックの外側に置けます。

## Configlue が扱うこと

<CardGrid stagger>
  <Card title="型付きの読み書き" icon="pencil">
    storage や serialization の詳細ではなく、`IReadOnlyState<T>` / `IWritableState<T>` に依存してアプリケーションを書けます。
  </Card>
  <Card title="複数設定の統合" icon="layers">
    user、local、environment、command-line、remote、database、custom source を重ねながら、値の出どころと編集可能性を保持します。
  </Card>
  <Card title="疎な書き込み" icon="pencil">
    generated patch により、missing、default、`null`、set、unset を区別し、モデル全体を雑に上書きしません。
  </Card>
  <Card title="schema の成長" icon="arrow-right">
    model version、migration、保存形状の変更、validation、JSON Schema の出力を扱えます。
  </Card>
  <Card title="運用を含めた永続化" icon="approve-check">
    変更通知、安全な保存、backup、conflict handling、対応形式での comment 保持、encryption、compression を必要に応じて組み込めます。
  </Card>
  <Card title="広い .NET integration" icon="puzzle">
    Plain .NET、DI、Microsoft Options、ASP.NET Core、Blazor、desktop UI、MAUI、Unity、Godot、R3、NativeAOT でも同じ state model を使えます。
  </Card>
</CardGrid>

## ひとつの state model を、さまざまな .NET アプリで

<CardGrid>
  <Card title="Plain .NET" icon="layers">
    `ConfiglueApp.Initialize(...)` で一度初期化し、`ConfiglueApp.GetState<T>()` から process-wide な型付き state を利用します。
  </Card>
  <Card title="Generic Host / ASP.NET Core" icon="puzzle">
    DI に Configlue を登録し、アプリケーションには `IReadOnlyState<T>` / `IWritableState<T>` だけを inject します。host integration から user / tenant 単位の state も構成できます。
  </Card>
  <Card title="Blazor / Desktop UI" icon="pencil">
    Blazor の `StateReader<T>` / `StateEditor<T>`、または共通 ComponentModel adapter を使い、各 host の native dispatcher と接続できます。
  </Card>
  <Card title="MAUI / Unity / Godot" icon="arrow-right">
    state abstraction はそのままに、各 host が適切な application path、lifecycle、storage、threading、runtime semantics を提供します。
  </Card>
</CardGrid>

## はじめる

最小の実行可能サンプルとインストール方法は、GitHub README の [Quick Start](https://github.com/arika0093/Configlue#quick-start) にあります。

まずは high-level な state API だけを使ってください。provider、resource、transformer、hosting package、低レベルの構成は、アプリケーションで必要になったときに追加できます。
