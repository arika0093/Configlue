# Configlue とは

## 名前は「糊」から来ています

Configlue は **Config + glue** です。複数の設定ソースを、糊（のり）で貼り合わせるように束ねるライブラリです。

たとえば、あるアプリの設定はこんなふうに散らばります。

- 出荷時の既定値が入ったファイル
- ユーザーが保存したファイル
- 会社から配られるポリシー（HTTP 配信など）
- コンテナに渡す環境変数
- デバッグ時だけ付け足すコマンドライン指定

置き場所も、決める人も、変わる頻度もバラバラです。Configlue はこれらを「糊づけ係」として引き受けます。各ソースは自分が知っている項目だけを差し出し、実行時にひとつの型付きモデルになります。

## 設定が壊れ始める順番

設定は、たいてい次の順番で扱いにくくなります。

1. 最初は JSON がひとつあれば足りる。
2. ユーザー別の保存が要るようになり、ファイルを分ける。
3. 環境変数やコマンドラインの上書きが増え、優先順位がコードに散らばる。
4. 一項目の保存がファイル全体の書き換えになり、よその項目やコメントを壊す。
5. 項目を増減・改名したとき、古いファイルの扱いが決まらず移行が止まる。

よくある対処は、その場しのぎの分岐を足すことです。最初は動きます。でも「どの値がどこから来たのか」がコードから読めなくなり、変更が怖くなります。

## Configlue の向き合い方

発想を逆にします。設定を「ひとつの木」として読むのではなく、**出どころごとの小さな寄与の集まり**として扱います。

- **ソースは項目を持つ。** ファイル全体でも、入れ子のセクションでも、環境変数の接頭辞でも、リモートの取得結果でも構いません。複数のソースが、ひとつのモデルの別々の部分を受け持ちます。
- **ないものは、ないまま扱う。** 生成コードが「未設定」と「`null` や既定値に設定」を区別します。重ねても、設定していない項目が既定値を上書きしません。
- **読みは重ね、書きは宛先指定。** 読み取りは優先度順に合成します。書き込みは既定でひとつのソース、必要なら項目ごとに複数の宛先へ振り分けます。関係ないソースは汚しません。
- **置き場所と形は別々に進化させる。** バイトの置き場所（Resource）、バイトと値の変換（Codec）、論理的な寄与（Source）を分けて考えます。形の変更は版管理で、置き場所の引っ越しは検証付きコピーで扱います。

このため、後からソースを足しても、古いファイルを捨てなくて済みます。詳しい仕組みは[設計の全体像](../design/overview.md)に、順番に触りたい方は[チュートリアル](./01-first-file-app.md)に進んでください。

## 向いている場面・向いていない場面

向いているのは、「増えた後の設定」です。出荷既定の上にユーザー設定を重ねる、ファイル・環境変数・コマンドラインを組み合わせる、プロファイルやドキュメント単位の設定を持つ、`appsettings.json` ひとつでは足りなくなった、といった場合です。

逆に、起動時に一度だけ読む静的な単一ファイルで、書き込みも重ね合わせも移行も要らないなら、素のオプションバインドや直接読みで十分です。無理に使う必要はありません。

## Configuration.Writable との関係

Configlue は [Configuration.Writable](https://github.com/arika0093/Configuration.Writable) の後継アーキテクチャです。「ひとつの型にひとつのファイル」から、「複数のソースを疎なフラグメントで重ねる」形に進めました。既存の JSON / YAML ファイルは、読み取り専用の移行入力として取り込めます。手順は[取り込みガイド](../migration/adopting-configuration-writable.md)を見てください。
